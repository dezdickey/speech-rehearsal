Bridge access-control test

Open this from disk, like any hostile page would be opened from the web. It is a different origin from the bridge either way.

1   Bare GET via an image tag

No JavaScript, no CORS involved. The same-origin policy does not stop a browser from loading an image, and the server acts on the request before anyone asks whether the page may read the reply.

v1 expected: slide 1 appears  |  v2 expected: no movement (405)
not run

2   Unauthenticated fetch of /health

Reconnaissance. Tells an attacker the bridge is running and which mode it is in.

v1 expected: JSON is readable  |  v2 expected: blocked or 401
not run

3   Command with no token

A POST to /goto with the custom header omitted. The browser will not even complete the preflight unless the server allows it.

v2 expected: rejected, and the slide does not move
not run

4   Command with a wrong token

Proves the credential is actually compared, not merely required to be present.

v2 expected: 401
not run

5   Command with the real token

The control case. If this fails, the tests above prove nothing — a bridge that rejects everything is not the same as a bridge that rejects the right things.

v2 expected: 200, and slide 3 appears
paste a token to run this one
Host validation cannot be tested from a browser. JavaScript is forbidden from setting the Host header, which is exactly why that check is worth having. Test it from a terminal instead: 
curl -i -X POST "http://127.0.0.1:8765/goto?n=2" ^
  -H "Host: evil.example" ^
  -H "X-Rehearsal-Token: PASTE_REAL_TOKEN"

REM v2 expected:  HTTP/1.1 403 Forbidden   {"ok":false,"error":"bad host"}
REM This is the DNS-rebinding defence. A real token is not enough on its own.
